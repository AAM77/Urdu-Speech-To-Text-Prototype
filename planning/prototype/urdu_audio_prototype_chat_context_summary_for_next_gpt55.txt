Primary prototype recommendation already made
=============================================
For the urgent prototype, the prior assistant recommended:

- Use exactly one chunk size by default.
- Use exactly one paid AI pass per stage by default.
- Recommended chunking strategy: 5-minute chunks with 60-second overlap.
- Do not use all four chunk sizes for the prototype.
- Do not perform multi-pass transcription/translation/review unless the user explicitly chooses to do so later.

Reasoning:
- 5-minute chunks are a good balance between context and cost.
- They are long enough to preserve lecture context better than very short chunks.
- They are short enough to retry and process safely.
- They avoid the high cost and complexity of processing 3-, 5-, 10-, and 30-minute chunk sets simultaneously.


Cost-control decisions
======================
The user wants strong cost limits.

Budget preferences:
- Ideal total cost: below $30.
- Absolute hard cap: do not exceed $60.

The previous discussion estimated that a sane best-quality run for a 60-minute audio file using one chunk set could plausibly be around $4-$8, while a full all-four-chunk-set strategy could be more like $12-$30 or higher depending on downstream passes and reviews. A careless max-cost strategy with repeated full context, retries, and cross-provider review could exceed $60.

The prototype should therefore:
- Default to one chunk set only: 5-minute chunks.
- Default to one pass per stage.
- Estimate cost before paid API calls.
- Avoid processing all chunk sets unless explicitly approved.
- Avoid cross-provider review in the prototype default.
- Avoid broad rolling/full-context prompts by default.
- Avoid retry loops that can cause API cost spikes.
- Mock/fake all provider calls in tests.
- Never make paid API calls in the test suite.


Model decisions already discussed
=================================
Transcription:
- Recommended OpenAI quality candidate: gpt-4o-transcribe.
- Recommended economy candidate: gpt-4o-mini-transcribe, but not the default unless evals prove it is acceptable.
- Recommended timestamp-precision candidate: whisper-1 or another timestamp-capable ASR provider, but not needed for the first prototype if synthetic/segment-level chunk timestamps are enough.
- Recommended diarization candidate: gpt-4o-transcribe-diarize only if speaker labels are needed. Speaker labels are not a default prototype requirement.

Why not GPT-5.5 for direct transcription:
- GPT-5.5/GPT-5.4 are text/image-input models and are not the current dedicated OpenAI speech-to-text transcription models.
- Use GPT-5.5/GPT-5.4 after transcription for cleanup, translation, article generation, and review, not for direct batch audio transcription unless OpenAI later releases a dedicated STT-capable GPT-5.x transcription model.

Translation/article generation:
- Best quality default: gpt-5.5, configurable.
- Balanced fallback: gpt-5.4, configurable.
- Economy fallback: gpt-5.4-mini only if the user later wants cheaper runs and evals prove acceptable.

Cursor coding/planning model:
- Use Cursor's strongest available model for planning and implementation.
- User specifically wants Cursor's Opus model to generate the prototype with minimal input.
- Avoid mini/nano/haiku-tier models for architecture, prompt-sensitive work, safety rules, or cost-control code.

Provider model IDs should be configuration-driven, not hardcoded throughout business logic.

Preferred approach from the prior assistant:

- Streamlit UI for fastest usability.
- CLI support for every stage.
- Simple local filesystem artifact storage.
- Optional simple JSON manifests.
- Avoid database-heavy production architecture unless needed.

The prototype should still be modular:
- chunker stage
- transcription stage
- translation stage
- article generation stage

Each stage should accept the previous stage's output as an uploaded/imported artifact.
Each stage should produce downloadable outputs and manifests.


Manual handoff requirement
==========================
This is important to the user.

The prototype must avoid forcing the user to restart from raw audio after every failure or change.

Required behavior:
- User can upload raw audio and run chunking.
- User can download chunk artifacts/metadata.
- User can upload chunk artifacts into transcription.
- User can download Urdu transcript artifacts.
- User can upload Urdu transcript artifacts into translation.
- User can download English translation artifacts.
- User can upload translation artifacts into article generation.
- User can download final article.

Artifacts should include both:

- prompt version

- segment IDs
- estimated cost and usage metadata where available
- upstream artifact references where available
