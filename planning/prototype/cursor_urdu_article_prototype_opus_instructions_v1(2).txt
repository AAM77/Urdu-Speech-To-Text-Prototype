CURSOR OPUS PROTOTYPE PLANNING INSTRUCTIONS
Urdu Audio Transcription → Urdu-to-English Translation → American English Article
Fast, Modular, High-Accuracy Prototype

Version: Prototype v1
Goal: Create a usable local prototype quickly.
Default processing: one pass, one chunk size, 5-minute chunks with controlled overlap.
Budget target: under $30 per 60-minute audio file.
Hard cost cap: $60.

==================================================
PURPOSE
==================================================

Use this document as the prompt/instruction document for Cursor using its strongest available Opus-class model.

The goal is NOT to build the full production application yet.

The goal is to quickly build a high-quality local prototype that can:

1. Accept an Urdu audio file that may contain Urdu, Arabic, and English.
2. Split it into one selected chunk set.
3. Transcribe the chunks into Urdu script.
4. Merge/reconcile the chunk transcripts into one clean Urdu transcript.
5. Translate the Urdu transcript into American English with religious/technical nuance preserved.
6. Generate one cohesive American English article.
7. Save and download every stage output.
8. Allow the user to manually upload any prior-stage artifact into the next stage.
9. Avoid rerunning expensive previous stages.
10. Stay under a $30 target whenever reasonably possible and never exceed $60.

Cursor/Opus should generate a detailed implementation plan first, then implement the prototype in modular, testable batches.

==================================================
HIGH-LEVEL PROTOTYPE DECISION
==================================================

Use a Python-first local prototype.

Recommended stack:
- Python 3.12+
- OpenAI Python SDK
- pydantic for schemas/artifact validation
- pytest for tests
- ffmpeg/ffprobe through subprocess or ffmpeg-python for audio chunking
- Streamlit for the fastest local UI
- Typer or argparse for CLI commands
- Local filesystem artifacts
- .env for API keys
- JSON manifests for resumability
- Markdown/text downloads for human-readable outputs

Avoid for this prototype unless absolutely necessary:
- multi-service Docker orchestration
- Redis queues
- Kubernetes
- full authentication
- PostgreSQL
- Prisma
- T3 stack
- tRPC
- complex background workers
- multi-provider bake-off
- all-four-chunk-set processing
- diarization
- word-level timestamp processing
- cross-provider review

Reason:
The user is short on time and wants to start using the system as soon as possible. A Python-first local prototype with clean modular boundaries is faster to implement and easier to run while still preserving the path toward the production architecture later.

==================================================
DEFAULT CHUNKING RECOMMENDATION
==================================================

Use exactly one chunk set by default:

- Chunk length: 5 minutes
- Overlap: 60 seconds
- Reason: 5-minute chunks are the best prototype compromise between accuracy, cost, context size, retry size, and implementation simplicity.
- Do not generate or transcribe 3-minute, 10-minute, or 30-minute chunk sets in the default prototype run.
- Do not transcribe all four chunk sets.
- Do not process multiple chunk sizes unless the user explicitly enables an advanced option later.

Important:
"Single chunk set" does not mean no overlap. Use one 5-minute chunk set with 60-second overlap. Each chunk is transcribed once. The overlap is used only to reduce boundary loss and support transcript reconciliation.

==================================================
MODEL DEFAULTS FOR PROTOTYPE
==================================================

All model IDs must be configurable in config, not hardcoded throughout the codebase.

Default model roles:

1. Transcription:
   - role: transcription_quality_model
   - default model: gpt-4o-transcribe
   - purpose: speech-to-text from Urdu/Arabic/English mixed audio to Urdu-script transcript
   - note: do not use GPT-5.5 for direct transcription because it is not the dedicated transcription model.

2. Translation:
   - role: translation_quality_model
   - default model: gpt-5.5
   - fallback model: gpt-5.4 if gpt-5.5 is unavailable or too costly
   - purpose: Urdu transcript to accurate American English translation

3. Article generation:
   - role: article_quality_model
   - default model: gpt-5.5
   - fallback model: gpt-5.4 if gpt-5.5 is unavailable or too costly
   - purpose: generate polished 8th-grade American English article

4. Transcript reconciliation:
   - role: reconciliation_quality_model
   - default model: gpt-5.5
   - fallback model: deterministic overlap dedupe + gpt-5.4 if cost requires

5. Optional validation:
   - role: validation_model
   - default model: gpt-5.4-mini only if needed
   - purpose: cheap output checks, never theological final authority

Before implementing real API calls, Cursor must verify:
- exact model IDs
- current API endpoint requirements
- input/output formats
- pricing
- whether the selected model supports the needed endpoint
- max file size and request limits
- response shape

Unit tests must never call real APIs.

==================================================
COST LIMITS
==================================================

Budget target:
- Try to keep a 60-minute audio file under $30 total.

Hard cap:
- Never exceed $60.
- The backend/core pipeline must enforce the cap.
- The UI alone is not sufficient.

Prototype default:
- One 5-minute chunk set only.
- One transcription pass.
- One reconciliation pass.
- One translation pass.
- One article generation pass.
- No cross-provider review.
- No multi-chunk-size eval.
- No expensive repeated full-context processing.
- No blind retries.

Cost controls:
- Estimate transcription minutes before calling the transcription API.
- Estimate text model tokens before translation/article calls.
- Show estimated cost by stage before the run starts.
- Require user confirmation before any paid API call.
- Include a 20% safety margin in estimates.
- Pause before making a call if projected cost plus safety margin would exceed the budget.
- Block calls if projected total would exceed $60.
- Cache outputs so rerunning the same stage does not repeat paid calls.
- Use checksums/hashes for cache keys.

Cache keys must include:
- input file hash or input text hash
- stage name
- model provider
- model ID
- prompt version
- chunk length
- overlap
- context mode
- relevant model parameters

Required stages:

   - reconciled_urdu_transcript.json

4. Translator

   - reconciled_urdu_transcript.json or reconciled_urdu_transcript.md

   - english_translation.json
   - english_translation.md
   - translation_manifest.json

5. Article Generator
   Input:
   - english_translation.json or english_translation.md
   Output:
   - final_article.json
   - final_article.md

   Input:
   - any stage artifacts
   Output:
   - downloadable individual files

Each stage must support:
- running from the UI
- running from CLI
- importing/downloading artifacts
- continuing from existing artifacts
- validating prior-stage artifacts
- refusing wrong-stage artifacts safely
- no dependency on in-memory state

Manual handoff must work:
- User can run chunker, download chunk artifact, later upload it into transcriber.
- User can run transcriber, download Urdu transcript, later upload it into translator.
- User can run translator, download English translation, later upload it into article generator.
- User can skip directly to translation if they already have a transcript.
- User can skip directly to article generation if they already have English translation.

==================================================

Every stage must produce:

1. Human-readable output:
   - Markdown or .txt

2. Machine-readable output:
   - JSON artifact

3. Manifest:
   - JSON manifest containing metadata and compatibility information

Minimum manifest fields:
- artifact_id
- schema_version
- stage_name
- created_at
- source_input_hash
- upstream_artifact_ids
- model_provider
- model_id
- prompt_id
- prompt_version
- chunk_length_seconds, where applicable
- overlap_seconds, where applicable
- context_mode
- estimated_cost
- actual_usage, if available
- cache_hit
- checksum
- warnings
- human_review_status

All timestamps must be stored in milliseconds where available.

For prototype:
- chunk-relative and absolute chunk start/end times are required.
- model-generated word-level timestamps are not required.
- segment-level timestamps are helpful but not mandatory if the transcription API does not return them.
- Synthetic chunk-level timestamp ranges are acceptable for the prototype.

==================================================
PROMPTS
==================================================

Prompts must be versioned files.

Do not bury prompts inside random Python strings unless they are loaded from prompt files.

Transcription prompt:
- Output Urdu script only.
- Do not translate into English.
- Preserve spoken English words.
- Preserve Arabic phrases where spoken.
- Mark unclear audio as [غیر واضح].
- Do not hallucinate.
- Use religious terminology awareness only to avoid mishearing terms, not to invent content.

Translation prompt:
- Input is Urdu text, not audio.
- Output is American English.
- Preserve meaning, nuance, religious terminology, idioms, and detail.
- Do not summarize unless instructed.
- Use Hans Wehr-style transliteration for technical Arabic/Urdu religious terms where appropriate.
- For technical/religious terms, use English translation first followed by italicized transliteration in parentheses.
- Preserve uncertainty markers.

Article prompt:
- Input is English translation, not audio.
- Output is one cohesive American English article.
- Target 8th-grade reading level.
- Preserve theological nuance and dignity.
- Do not introduce new claims.
- Use logical headings and paragraph breaks.
- Remove transcript-like filler.
- Preserve important religious terminology.

Reconciliation prompt:
- Merge overlapping chunk transcripts.
- Remove duplicate overlap content.
- Preserve the best wording.
- Do not add new content.
- Preserve uncertainty markers.
- Keep source chunk references where possible.

PROTOTYPE PIPELINE BEHAVIOR
==================================================

Default one-click pipeline:

1. User uploads audio.
2. App probes duration and file metadata.
3. App estimates cost.
4. App shows:
   - selected chunk length: 5 minutes
   - overlap: 60 seconds
   - transcription model
   - translation model
   - article model
   - estimated cost
   - budget
5. User confirms.
6. Chunker creates chunks.
7. Transcriber transcribes each chunk once.
8. Reconciler merges/deduplicates overlap.
9. Translator translates reconciled transcript.
10. Article generator creates final article.
11. App shows downloadable outputs for every stage.

The user must also be able to run each stage separately.

==================================================
ACCURACY GUARDRAILS
==================================================

For high accuracy in the prototype:

1. Use 5-minute chunks with 60-second overlap.
2. Use the transcription prompt with Urdu script only.
3. Use a short glossary/context section in prompts for Islamic terms.
4. Preserve uncertainty markers.
5. Reconcile overlap before translation.
6. Translate the reconciled Urdu transcript, not each raw chunk independently, unless the transcript is too long.
7. If transcript is too long for one translation call, split by timestamped segments and carry forward a small terminology context packet.
8. Generate the article from the reconciled English translation.
9. Do not allow article generation directly from raw chunk transcripts unless translation exists.
10. Do not hide uncertainty; carry it through.

Prototype glossary should be editable in:
src/urdu_pipeline/prompts/glossary.md

The glossary may include:
- Allāh

- sunnah
- sharīʿah
- fiqh
- Māturīdī
- Ḥanafī
- taṣawwuf
- ʿulamāʾ

Do not force transliteration in the Urdu transcript stage.
