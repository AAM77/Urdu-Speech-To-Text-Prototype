# ADR 0003: Opaque Object Keys

Date: 2026-06-06

Status: Accepted

## Context

The API migration will move uploads, intermediate files, stage artifacts, and
cache entries into durable object storage. Object keys are operational
identifiers, and public API responses must not turn them into user-facing
identity, authorization, or filename data.

Original filenames can contain personal information, path-like values, Unicode
normalization surprises, misleading extensions, or names that are awkward to
sanitize consistently across providers. Even sanitized filenames can leak user
context or become compatibility constraints for object-store adapters.

## Decision

Durable object keys must be opaque storage identifiers generated by the server.
Object keys may include server-generated IDs and fixed structural prefixes, but
they must not include original filenames, sanitized filenames, user-submitted
path fragments, display names, prompt names, model names, provider names, raw
artifact titles, or other user-controlled labels.

Original filenames and sanitized filenames are metadata only. They may be kept
for audit records, UI display, or optional signed-download display names, but
they must not determine the object key.

Signed upload and download flows must use server-owned object references and
authorization checks. Public API responses should expose stable resource IDs and
download URLs when appropriate, not raw object keys.

## Consequences

- Object-store adapters can target S3-compatible stores, MinIO, R2, or future
  storage backends without inheriting filename-specific behavior.
- Object keys are less likely to leak user content, original filenames, or
  provider details through logs, URLs, or error messages.
- Filename display and storage addressing remain separate concerns.
- Migrations can reshape storage prefixes without changing user-visible file
  names.
